## 一、总体架构：分层 + 单向依赖

系统分为 **4 块**，依赖方向严格单向：

```
        ┌──────────────────────────────────────────────┐
        │  ③ UI 层   src/ui/                           │
        │  职责：显示数据、收集用户输入                  │
        │  知道：Qt 控件、core 层的接口                  │
        │  不知道：文件怎么读、业务规则是什么             │
        └───────────────────┬──────────────────────────┘
                            │ 调用（只能向下）
        ┌───────────────────▼──────────────────────────┐
        │  ② 逻辑层   src/core/                        │
        │  职责：全部业务规则、全部文件读写               │
        │  知道：数据结构、规则、文件格式                 │
        │  不知道：界面的存在（不 include 任何 QtWidgets）│
        └───────────────────┬──────────────────────────┘
                            │ 使用
        ┌───────────────────▼──────────────────────────┐
        │  ① 模型层   src/model/                       │
        │  职责：只定义「数据长什么样」                   │
        │  不含任何逻辑，不依赖任何其他模块               │
        └──────────────────────────────────────────────┘
                            ▲
        ┌───────────────────┴──────────────────────────┐
        │  ④ 资源   src/resources/                     │
        │  QSS 样式表、图标等，被 UI 层引用               │
        └──────────────────────────────────────────────┘
```

### 两条铁律

1. **UI 层不许直接碰文件** —— `src/ui/` 里出现 `QFile` / `QDataStream` 即为违规。
2. **逻辑层不许出现界面** —— `src/core/` 里出现 `QWidget` / `QMessageBox` 即为违规。

守住这两条，工程不会烂。

### 依赖细化（关于 Qt 模块）

| 代码块 | 需要的 Qt 模块 |
|---|---|
| `model/` + `core/` | 只需 **QtCore**（QString / QFile / QDateTime / QMap / QList） |
| `ui/` | 需要 **QtWidgets**（= QtGui + QtCore） |

即：**整个逻辑层与界面库完全无关**，这也是铁律 2 的另一种表述。

### core 内部的依赖

```
FileStore       ← 无依赖
AppClock        ← 无依赖
TrainManager    ← FileStore
UserManager     ← FileStore
TicketManager   ← FileStore, TrainManager（需读班次、回写已售数）
```

## 三、模块职责

### 3.1 model 层（①）

纯数据定义，**只有 `.h`，没有 `.cpp`，不含任何函数实现**。

| 文件 | 内容 |
|---|---|
| `Result.h` |  `Result` 结构体 —— 全部业务函数的统一返回值 |
| `Train.h` | `Train` 结构体 —— 一个车次 |
| `Ticket.h` | `Ticket` 结构体 —— 一张票 |
| `User.h` | `Role` 枚举 + `User` 结构体 |

### 3.2 core 层（②）

| 类 | 职责 | 关键点 |
|---|---|---|
| `AppClock` | 提供全系统唯一的「当前时间」 | 可切换到模拟时间，用于演示 |
| `FileStore` | 四个数据文件的读写 | 二进制用 `QDataStream`，文本用 `QTextStream` |
| `TrainManager` | 班次的增删改查、排序、余票与状态计算 | 内存中持有 `QList<Train>` |
| `TicketManager` | 售票、退票、实名制判定、全部规则校验 | 持有一个 `TrainManager&` |
| `UserManager` | 注册、登录、身份证校验、权限判定 | 内存中持有 `QList<User>` |

### 3.3 ui 层（③）

| 窗口 | 职责 |
|---|---|
| `MainWindow` | 角色选择首页；显示当前系统时间；进入时钟设置 |
| `LoginDialog` | 三种角色共用，靠 `Role` 参数区分校验目标 |
| `RegisterDialog` | 乘客身份证注册 |
| `AdminWindow` | 班次表格 + 增 / 改 / 删按钮 |
| `TrainEditDialog` | 班次表单，含全部字段校验 |
| `UserWindow` | 日期筛选 + 班次表格 + 查询 + 生成时刻表 + 我的车票 |
| `SellerWindow` | 售票面板 + 退票面板 + 售况统计 |
| `TrainTableWidget` | 被三个窗口复用的班次表格（9 列，状态列带颜色） |

### 3.4 resources（④）

`style.qss` 提供配色（状态列颜色区分：绿=正常售票 / 灰=此车已发出 / 红=已满员）。

## 四、数据结构定义

```cpp
// ---------------- model/Result.h ----------------
struct Result {
    bool    ok = false;
    QString message;      // 失败原因，可直接丢进 QMessageBox
};
// 用法：
//   return { true,  {} };                          // 成功
//   return { false, QStringLiteral("余票不足") };   // 失败


// ---------------- model/Train.h ----------------
struct Train {
    QString         trainNo;       // 车次号      G1113
    QTime           departTime;    // 发车时间    07:25（每天都是这个点）
    QString         startStation;  // 起点站      南京南
    QString         endStation;    // 终点站      广州南
    double          hours;         // 行车时间    7（小时）
    int             capacity;      // 额定载量    600
    double          price;         // 票价        553.5（自选拓展字段）

    // 各乘车日期的已售票数：key = 乘车日期，value = 该日已售张数
    // 注意：没有「日期」字段，日期是运行时的查询维度
    QMap<QDate,int> soldByDate;
};
// 派生量：余票 = capacity - soldByDate.value(date, 0)


// ---------------- model/Ticket.h ----------------
struct Ticket {
    QString   idCard;       // 身份证号
    QString   name;         // 姓名
    QString   trainNo;      // 车次号
    QDate     travelDate;   // 乘车日期  ← 即「运营日」
    QDateTime sellTime;     // 售票时间
};


// ---------------- model/User.h ----------------
enum class Role { Admin, Seller, Passenger };

struct User {
    QString account;    // 管理员/售票员用账号；乘客用身份证号
    QString password;
    QString name;       // 姓名（乘客）
    Role    role = Role::Passenger;
};
```

## 五、核心接口

### 5.1 AppClock —— 统一时间入口

```cpp
class AppClock {
public:
    static QDateTime now();                    // 全系统唯一时间出口
    static void      setMock(const QDateTime&);// 设定模拟时间
    static void      clearMock();              // 恢复真实系统时间
    static bool      isMocked();
};
```

> **强制约定**：业务代码中**禁止**出现裸的 `QDateTime::currentDateTime()`，一律走 `AppClock::now()`。
> 目的：答辩时点一下「设为发车前 20 分钟」，就能演示「发车不足 30 分钟不能退票」。

## 六、业务规则（核心）

### 6.1 售票条件（三条全部满足）

```
① 已售票数 < 额定载量
② 当前系统时间 < 该车次该日期的发车时刻
③ 该乘车日期在提前售票期内（默认：今天起 15 天内）
④ 实名制：该身份证在该车次该日期没有已购票
```

### 6.2 退票条件（两条全部满足）

```
① 该车次尚未发出（当前时间 < 发车时刻）
② 距发车时刻 ≥ 30 分钟
```

### 6.3 车次状态显示

| 条件 | 显示 |
|---|---|
| 当前时间 ≥ 发车时刻 | **此车已发出** |
| 余票 ≤ 0 | **已满员** |
| 其他 | **正常售票** |

### 6.4 时序关键点

发车时刻 = `QDateTime(乘车日期, 发车时间)`

```cpp
QDateTime departDateTime(const Train& t, const QDate& date) {
    return QDateTime(date, t.departTime);
}
```

## 七、文件格式

### 7.1 `number.dat`（二进制，`QDataStream`）

```
文件头： 魔数 "TTKT" (4 字节)  |  版本号 quint16  |  班次总数 quint32
每条班次：
    trainNo       QString
    departTime    QTime
    startStation  QString
    endStation    QString
    hours         double
    capacity      qint32
    price         double
    soldByDate    QMap<QDate, qint32>
```

- 读写前必须调用 `stream.setVersion(QDataStream::Qt_6_0)`，否则换 Qt 版本后读不出来。
- 文件头魔数用于校验文件完整性，不匹配则提示「数据文件格式错误」。

### 7.2 `tickets.dat`（二进制）

```
文件头： 魔数 "TTKT" | 版本号 quint16 | 票总数 quint32
每张票： idCard QString | name QString | trainNo QString
         travelDate QDate | sellTime QDateTime
```

### 7.3 `users.dat`（二进制）

```
文件头： 魔数 "TTKT" | 版本号 quint16 | 账号总数 quint32
每个账号： account QString | password QString | name QString | role qint32
```

### 7.4 `sort.dat`（纯文本，UTF-8）

按发车时间升序排列的时刻表，表头照抄题目给出的表格：

```
车次      发车时间   起点站    终点站   行车时间  额定载量  余票数量
G1113     07:25     南京南    广州南   7         600       570
G1887     07:39     南京南    重庆西   12        700       660
G180      12:22     南京南    北京南   5         700       580
G1210     13:05     上海虹桥  济南西   4         800       798
```

> 「余票数量」列填写的是**指定乘车日期**的余票（默认今天）。

## 八、关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **乘车日期（运营日）放在 `Ticket` 里，不放进 `Train`** | 班次是「每天开行的车次」，日期是查询维度。这样 `number.dat` 保持题目给的 7 列结构，不膨胀 |
| 2 | **已售票数存进 `Train.soldByDate`（按日期）** | 对应题目表格「余票数量」列，且满足原文「自动更新已售票人数」。按日期存是为了同时支持多天查询 |
| 3 | **启动时执行一次 `reconcile()` 对账** | 冗余计数与票表可能不同步（忘改、写文件中断等）；以票表为准覆盖一次，结构性地消灭不一致 |
| 4 | **余票不单独存**，由 `capacity - soldByDate[date]` 算出 | 避免第三个数据源 |
| 5 | **统一走 `AppClock::now()`** | 演示「发车已过」「停止退票」必须能操控时间 |
| 6 | **一证一票 = 同一车次 + 同一乘车日期限购一张** | 题目原文「每张身份证只允许购买一张」在支持多天车次后不合理；答辩时主动说明 |
| 7 | **退票 = 距发车不足 30 分钟则不能退** | 题目原文「当本车次发出前半小时才可以退票」语义模糊；答辩时主动说明 |
| 8 | **登录对话框三合一** | 三种角色只是校验目标不同，用一个 `LoginDialog(Role)` 省两份重复代码 |
| 9 | **班次表格控件三合一** | `TrainTableWidget` 被管理员、乘客、售票员三个窗口复用 |
| 10 | **界面使用 `QTableWidget` 而非 `QTableView + Model`** | 数据量小（几十行），Model/View 属过度设计 |

## 九、编码约定（跨平台安全）

以下约定用于消除「本机编译验证」与「Windows 实际编译」之间的差异：

| # | 约定 | 原因 |
|---|---|---|
| 1 | **禁止 `QString::fromLocal8Bit` / `toLocal8Bit`**，统一用 `fromUtf8` / `toUtf8` | 本机按 UTF-8 解释，Windows 按 GBK 解释，同代码不同结果且编译期无感 |
| 2 | **显式 include**，用到什么写什么 | 不依赖某个编译器「恰好间接引入」了某个头文件 |
| 3 | **不写平台分支**，代码中不出现 `#ifdef Q_OS_WIN` | 单一目标平台，没必要引入差异 |
| 4 | **不使用 `QFileDialog`** | 数据文件名固定，不需要文件对话框（该控件平台差异最大） |
| 5 | **CMake 中不写 `if(WIN32)` / `if(UNIX)` 平台分支** | 同上 |
| 6 | **路径一律用 Qt 类拼接**，不手写 `"/"` 或 `"\\"` | 用 `QDir` / `QCoreApplication::applicationDirPath()` |
| 7 | 源文件一律 **UTF-8（无 BOM）** | Qt Creator 默认，MinGW 默认按 UTF-8 读源码 |
| 8 | 所有 `connect` 使用**函数指针语法** | 编译期就能查出信号槽签名不匹配，而不是运行时静默失败 |
| 9 | 每个带信号槽的类**必须写 `Q_OBJECT`** | 漏写会报 `undefined reference to vtable` |

### 版本与工具链

| 环境 | Qt 版本 | 编译器 | 构建系统 |
|---|---|---|---|
| **Windows（目标平台）** | **6.10.2** | MinGW 13.1 64-bit | **CMake** |
| Ubuntu（PRoot，**权威验证环境**） | **6.10.2**（与目标同版本） | g++ 15 | CMake |
| Termux（安卓，备用冒烟测试） | 6.11.2 | clang 21 | qmake |

**版本策略：本机验证环境与目标平台对齐。**

- Windows 端安装 **Qt 6.10.2**，与本机 Ubuntu 环境**版本完全一致**，
  因此「本机编译通过」与「Windows 编译通过」之间的版本差异为零。
- Termux 环境为 6.11.2（更高版本），只能用于提前发现语法错误，
  **不能**作为「6.10.2 可编译」的证明（高版本能编 ≠ 低版本能编）。
- 仍保持一条纪律：只使用成熟 API、不追新特性；引入不熟悉的 API 前先查官方文档。
- 项目用到的 API 绝大多数是 Qt 4 / Qt 5 时代就存在的类（见第四节），
  因此触碰新版本 API 的可能性极低。

## 十一、开发与验证流程

```
我：写代码 → 本机 cmake 编译通过 → git commit → git push
                                    ↓
你：Windows 上 git pull → Qt Creator 打开工程目录（CMakeLists.txt）→ Ctrl+R 编译运行
```

### 本机编译验证能覆盖什么

| 问题类型 | 能否覆盖 |
|---|---|
| 语法错误、拼错函数名、漏 include、参数类型不对 | ✅ 能 |
| `Q_OBJECT` 漏写、信号槽签名不匹配 | ✅ 能 |
| 逻辑错误（规则判错、算错） | ✅ 可用控制台 `main` 验证 |
| 使用了本机有、Windows 端没有的新 API | ❌ 不能（靠版本对齐规避） |
| 编译器差异导致的隐式包含 | ❌ 不能（少见） |
| 平台相关运行时行为（编码、路径） | ❌ 不能（靠第九节约定规避） |
| 界面观感、字体、DPI 缩放 | ❌ 不能 |
| 运行时崩溃（越界、空指针） | ❌ 不能 |

> **定位**：本机编译是「提前排错」手段，把低级错误挡在交付之前；
> **不是**「保证 Windows 能编过」的证明。最终以 Windows 上的编译与运行为准。
